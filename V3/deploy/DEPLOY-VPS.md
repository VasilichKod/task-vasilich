Однократное подключение владельцем в своём Terminal (пароли скрыты):

```bash
python3 '/Users/stepansavelev/VCode/Автоматизации и N8N/TaskVasilich/V3/deploy/connect-mailru.py'
```

Мастер проверяет вход, шифрование аварийного ключа и обратную расшифровку,
не меняет прежние crypt-ключи при повторном запуске, передаёт секреты по SSH
и включает облачный таймер только после успешной авторизации. Успех мастера
означает завершённую первую выгрузку с readback; не просто запуск службы.
При смене аккаунта действующий конфиг не перезаписывается автоматически.

Проверки на сервере:

```bash
systemctl status task-vasilich-cloud-backup.service --no-pager
python3 /usr/local/lib/nedplan-backup/cloud-backup.py --check
systemctl list-timers 'task-vasilich-*'
```

Статус: `/var/backups/task-vasilich/cloud-status.json`. `--check` требует
последний успешный запуск и проверенную выгрузку не старше 8 часов.
Конфиг: `/etc/task-vasilich-backup/rclone.conf`, аварийный файл рядом
`recovery.conf.enc`. Секреты и ответы авторизации не выводить в диагностику.

Если потеряны VPS и Mac: скачать ключевой `.conf.enc` через сайт Mail.ru,
скопировать его в закрытый локальный каталог и выполнить
`rclone --config <копия-ключа> config encryption remove`, введя фразу владельца.
При истёкшем пароле Mail.ru заново авторизовать ТОЛЬКО raw remote,
crypt password/password2 не менять. Скачать комплект через `nedplan_secure:`,
сверить внешний SHA256 и внутренний манифест, изучить пути архива без
распаковки поверх `/`. Базу сначала восстановить в отдельный тестовый PostgreSQL17+.
Только после сравнения данных планировать замену рабочей установки.

Проверка без аккаунтов: `python3 V3/deploy/test-cloud-backup.py` использует
настоящий rclone crypt и временное локальное хранилище, не реальные облака.
Официальная документация backend: https://rclone.org/mailru/.

## Решение по запуску

Для VPS берём `systemd`, не `pm2`.

Почему:
- встроено в Linux
- переживает reboot сервера
- не добавляет лишний runtime-слой
- проще логировать и админить через `systemctl` и `journalctl`

## Что подготовить на VPS

1. Установить:
   - `git`
   - `nodejs`
   - `npm`
   - `postgresql`
   - `nginx`

2. Клонировать проект:
   ```bash
   git clone https://github.com/VasilichKod/task-vasilich.git /var/www/task-vasilich
   cd /var/www/task-vasilich/V3
   ```

3. Создать `.env` по шаблону:
   - см. `deploy/.env.production.example`

4. Установить зависимости:
   ```bash
   npm install
   ```

5. Применить миграции:
   ```bash
   npm run prisma:generate
   npm run prisma:migrate:deploy
   ```

## Запуск через systemd

1. Скопировать unit:
   ```bash
   sudo cp deploy/task-vasilich-v3.service /etc/systemd/system/task-vasilich-v3.service
   ```

2. Проверить `User`, `WorkingDirectory`, `EnvironmentFile`, `ExecStart` в unit-файле.

3. Перечитать systemd и запустить сервис:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable task-vasilich-v3
   sudo systemctl start task-vasilich-v3
   ```

4. Проверить статус:
   ```bash
   sudo systemctl status task-vasilich-v3
   ```

5. Смотреть логи:
   ```bash
   journalctl -u task-vasilich-v3 -f
   ```

## Nginx

Backend слушает `127.0.0.1:3000`.

Nginx должен:
- принимать `443`
- проксировать в `http://127.0.0.1:3000`
- отдавать SSL

`BIND_HOST` на production должен оставаться `127.0.0.1`, чтобы не открывать Node.js-порт в интернет в обход HTTPS.

Если перед origin-сервером используется edge reverse proxy, его nginx-конфиги находятся в:

- `deploy/nginx.nedplan-edge.conf` — `nedplan.ru` и `www.nedplan.ru`;
- `deploy/nginx.additional-edge.conf` — `podo.nedplan.ru`, `english.nedplan.ru`, `hel27.ru` и `www.hel27.ru`.

Связь edge → origin идёт по HTTPS с проверкой сертификата. На edge-сервере Certbot обновляет отдельные сертификаты для каждого домена.

Актуальный workaround для фильтрации TLS 1.3 через ТСПУ описан в `deploy/TSPU-TLS12.md`.
